**Current readiness: not filing-ready from the evidence reviewed.** The code and notice do not establish the controller’s legal identity, the existing CNDP receipt/authorization (if any), the actual list of purposes and legal bases, the number of affected people, effective retention/deletion, vendor contracts, or actual hosting/transfer countries. No current production environment or database was inspected. Under the current CNDP website guidance, the responsible party should resolve the processing-notification route and any foreign-transfer filing with the CNDP before treating this as compliant. This report does not determine which declaration or authorization applies.

**High-priority findings for the owner and Moroccan counsel/CNDP:**

1. **CNDP form classification is inconsistent.** The CNDP treatment page calls F214 a simplified declaration, while the linked current F214 PDF is titled *Déclaration normale conformément à une décision* and asks for a decision number. Do not pick F214, F211, F112, or F113 by inference; ask CNDP which current procedure applies to this service. The F118 transfer request must also be sequenced with approval of the underlying processing. See [X1–X7](#external-sources-checked-on-2026-09-26).
2. **The current public notices are materially out of sync with code.** They omit machine-translation providers and text transfer, underdescribe the public-profile fields, describe an analytics sender not found among the reviewed API routes, claim a browser fingerprint where the inspected code sends user-agent, and conflict on self-service deletion. The notice also says retained audit records contain no identifying data, but the profile-audit trigger stores full old/new profile JSON and IP data.
3. **Public profile privacy flags are not a sufficient database boundary in the reviewed code.** The public page fetches a wide `mizan_profiles` column list and masks some values in the browser. The table’s public RLS policy is row-based (`is_public = true`); the migration itself says a direct table read would leak city and bio and adds a safer RPC, but the frontend fetch reviewed here does not call that RPC. The public UI also displays fields the notice says are never public (notably years of experience and, when the XP panel is shown, credits). **Confirm effective grants and test anonymous REST access against production without exposing records.**
4. **Analytics is not one consent-gated path.** The app writes page-view rows to Supabase on public navigation without an inspected cookie-consent check. The Google tag code starts with `analytics_storage: denied` but still loads `gtag.js` at idle when a Google Analytics ID is configured. Google documents that advanced Consent Mode can send cookieless pings while consent is denied; actual network behavior and whether an ID is configured are **OWNER CONFIRMATION REQUIRED**. The internal page-view writer is separate from that Google choice.
5. **The deletion plan is not proven to run end-to-end.** The request endpoint marks `profiles.account_status = pending_deletion`; the migration supplies a 30-day candidate list and billing-anonymization RPC, but no deployed scheduled worker/cron was verified. The request does not itself hide the `mizan_profiles` public row. The baseline `audit_logs.user_id` FK to `auth.users` has no `ON DELETE` action, while the deletion request’s profile update triggers an audit row. This can obstruct final Auth deletion if those rows exist. The deletion notice and Terms page also conflict.
6. **Payment and credit schemas are inconsistent.** Two in-scope migrations define incompatible `credit_transactions` shapes; the later one assumes `user_ref`/`type` while an earlier one creates `user_id`/`direction`. The 2026-09-21 migration also defines a public `SELECT USING (true)` policy. A later-dated 2026-09-27 file exists in the repository but is beyond this audit cut-off and is not evidence of a deployed repair. **OWNER CONFIRMATION REQUIRED** for the live schema, migrations, access, writers, and records.
7. **Potential foreign transfers are numerous but not geographically verified.** Supabase, Cloudflare, Google, Stripe, and machine-translation services appear in the code or assets. The actual project/bucket/provider regions, contractual roles, signed DPAs, and configured providers are not in the reviewed repository. The CNDP transfer register cannot be completed from code alone.
8. **Payment creation endpoints lack visible caller authentication in the inspected handlers.** `/api/payments/create` accepts caller-supplied `userRef` and uses a service-role key to create a pending row; the conditional Stripe checkout routes likewise accept request-supplied identifiers and create sessions without a visible identity check. Confirm production exposure and restrict/verify ownership before treating payment records or user references as trustworthy.

**Recommended immediate disposition:** freeze any claim that the repo proves CNDP compliance; identify the controller and deployed configuration; request CNDP clarification on F214/F211 and authorization triggers; complete a factual provider/country and retention register; validate the public-profile and analytics paths; and test the actual 30-day deletion workflow before drafting/submitting any form.
